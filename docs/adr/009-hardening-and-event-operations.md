# ADR-009: Hardening and event operations

- **Status:** Accepted, 2026-10-07 (Phase 7). Closes the Phase 0, 1 and 5 backlog items R-1, R-2, R-6, the narrow-`env_file` item and the database-error-log item. R-3 and R-A2 stay open (see Consequences).

## Context
By the end of Phase 6 every feature is built and reviewed twice. What is left is what separates "works on my laptop" from "safe to run for a thousand people tomorrow": a smaller blast radius if one part is compromised, and a way for the organisers to know, in one minute, whether the system is ready to open.

## Decisions

### 1. The API connects to Postgres as `mc_app`, not as the owner (R-6)
Until now the API used the database owner, which is also a superuser in this stack. One SQL-injection bug (none is known; every query is parameterised) could then have switched off the vote and audit-log triggers, rewritten the votes or read the server's files.

- The **migrate** step connects as the owner, builds the schema, then provisions `mc_app` (`db/provision.ts`): `LOGIN`, no superuser, no `CREATEDB/CREATEROLE`, no replication, no RLS bypass, connection limit 60, 30 s idle-in-transaction timeout.
- Privileges are an **explicit allow-list rebuilt from scratch on every start** (`REVOKE ALL` on schema, tables and sequences, `CREATE` on the schema removed from everyone, then `GRANT`): `SELECT, INSERT` on everything; `UPDATE` only on the 9 tables the application changes; `DELETE` only on the 7 where it removes rows (sessions, recovery codes, OTP challenges, catalog rows, photos). **Never** `UPDATE`/`DELETE` on `votes`, `audit_log`, `visitors`, `settings`, `sms_outbox`. A table added later is invisible to the API until it is listed (fail closed). No `TRUNCATE`, `TRIGGER`, `REFERENCES`, or schema `CREATE`.
- The role cannot switch triggers off, set `session_replication_role`, `COPY … PROGRAM`, create roles or alter tables. `provision.test.ts` asserts each of these gets SQLSTATE 42501.
- The **whole integration suite runs as `mc_app`** (global setup provisions it; `openTestDb` hands tests the restricted pool and a separate owner pool for resets). 361 tests prove the application never needs more than the allow-list. Tests of the schema's own guards (checks and triggers) connect as the owner on purpose: the triggers must hold even against a privileged connection. Two layers, each tested.
- `server.ts` logs a warning if it finds itself connected as a privileged role; `pnpm stack:preflight` fails the event if `mc_app` is missing or privileged.
- The password lives in `.env` as `APP_DB_PASSWORD` (generated by `scripts/gen-env.mjs`); only the API replicas and the migrate container receive it. The owner password goes to **migrate only**.

*Rejected:* row-level security (the threat is the connection's rights, not a tenant boundary); a second database for the audit log (more moving parts than the risk justifies); making the API refuse to boot as a privileged role (a misconfigured laptop at the event should degrade loudly, and the preflight is the gate).

### 2. Containers get only what they need
- **No `env_file`.** The API receives an explicit list of variables. The tunnel token, the ngrok token and the Postgres owner password never enter an API container (the Phase 2 backlog item).
- API replicas: read-only filesystem (`/tmp` is a tmpfs), all capabilities dropped, `no-new-privileges`, 256 processes, 1 GB memory, already non-root (`node`).
- Caddy (R-2): runs as uid 1000, read-only, no capabilities, `no-new-privileges`. Port 80 is allowed by a sysctl on that container only. The stock image's binary carries a file capability that a capability-less container cannot execute, so the image ships a plain copy.
- `/api/readyz` is answered with 404 at the edge (R-1): it names the dependency that is down. Containers and operators check it from inside the network.

### 3. Errors are logged without their values
Drizzle puts bound parameters in the message of a failed query and the driver adds row values in `detail`. `lib/log-scrub.ts` is the logger's `err` serializer: it keeps the type, SQLSTATE, constraint, table, the SQL text and the stack, and drops the parameters and `detail`. A session token or a phone hash can no longer reach the logs through a database fault (Phase 5 backlog).

### 4. Two operator commands for event day
- `pnpm stack:preflight` (read-only) answers "can we open the doors?": SMS provider is the real one, no demo mode, production build, https origin, the venue gate is on with ranges (and warns about missing IPv6), at least two super admins with authenticators, categories with at least two exhibitors, no leftover demo content, photos present, a TV token exists, Wi-Fi details set, no rehearsal data, the application role is restricted, Redis, the tunnel answers, `/api/readyz` is hidden, no third-party analytics beacon is being injected. Exit code 1 on any FAIL. The rules are a pure function with tests (`ops/preflight.ts`).
- `pnpm stack:reset-event` clears rehearsal visitors, votes, OTP challenges and stored demo SMS. With no flags it only reports the counts. To delete you pass the confirmation word **and the exact vote count** (`--expect-votes=N`), so a recalled command cannot erase a finished event; voting must not be OPEN, and both conditions are checked again inside the deleting transaction with the settings row locked. It keeps organisers, settings, content, photos, TV tokens and the audit log, and writes an audit entry. `--with-content` also deletes exhibitors, categories, their links and photos (and resets the results display to LIVE, since the frozen snapshot and reveal list name those categories); the audit log is still never touched. It runs as the owner from the operator container, a privilege the API deliberately lacks (it has to step over the vote triggers, once).

### 5. Evidence for the scale claim is a repeatable script
`load/` holds the k6 scenario, the helpers and a one-command runner (`node load/run.mjs smoke|event|stress [--chaos]`) that builds a throw-away database, runs the whole visitor journey for up to 1,000 virtual visitors through Caddy to two replicas, holds 20 TV streams open, optionally kills each replica in turn, then checks the database against what the visitors were told. The report is `docs/load-test-report.md`.

## Consequences
- Operationally the stack now needs `APP_DB_PASSWORD` in `.env`; an old `.env` without it fails fast with a clear message, and `node scripts/gen-env.mjs` adds just that line to an existing file (it never regenerates the other keys).
- **R-3 (`style-src 'unsafe-inline'`) stays, accepted.** React and the animation code set inline `style` attributes; removing the allowance needs a nonce or hash scheme for every one of them, which is not a safe change on the last day. Impact is limited: scripts remain `'self'` only, so injected markup cannot run code.
- **R-A2 (admin reachable from the internet) stays an owner decision.** MFA, lock-out, per-address limits and the audit log carry it. A Cloudflare Access / WAF rule on `/admin*` and `/api/admin*` restricts it without a code change (runbook).
- **R-5 (the laptop is the single point of failure) is a demo-host decision**, mitigated by mains power, a hotspot and the recorded video; the replica kill test shows the application layer has none.
- Not done on purpose: a read replica or second Postgres (out of scope for a two-day build; `docs/deployment.md` describes the production topology).
